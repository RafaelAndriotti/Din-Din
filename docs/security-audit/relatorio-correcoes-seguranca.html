Resumo executivo

A auditoria apontou uma causa raiz: a API não tinha autenticação nem dono dos dados. A correção atacou essa causa primeiro e, sobre ela, fechou o resto. Agora toda rota fora de /auth exige um token, toda query de despesas e categorias filtra pelo dono do token, e o registro de outra pessoa responde 404. Por baixo, entraram as duas camadas que faltavam: a API conecta ao banco com uma role sem superusuário, e API e Postgres só aceitam conexões da própria máquina. A configuração é validada no boot, os erros não vazam detalhes internos, e as listagens têm paginação e rate limit. Os 18 itens do escopo foram corrigidos e verificados com testes automatizados, com Postgres real e no navegador. Ficaram de fora os dois informativos (F15 e F16), que não são exploráveis hoje.

Decisões de desenho, e por quê

Token no cabeçalho, não em cookie
Com Authorization: Bearer, o navegador não envia a credencial sozinho, então não existe CSRF. O custo é guardar o token em JavaScript (ver a seção 6).
scrypt da biblioteca padrão
O node:crypto já traz o scrypt, um hash lento de propósito, como argon2 e bcrypt, sem dependência nativa para compilar. Os parâmetros (N=2^15, r=8, p=3, do OWASP) ficam gravados no próprio hash, então dá para endurecê-los depois sem invalidar as senhas existentes.
Posse dentro da query, 404 para o que não é seu
WHERE id = $1 AND usuario_id = $2 confere e age numa ida só ao banco, sem janela entre checar e alterar. Responder 404, e não 403, não confirma que o ID existe.
O dono vem do token, nunca do cliente
usuario_id não existe nos schemas Zod, então o z.object descarta o campo se ele vier no body. O controller usa só req.usuarioId.
Duas roles no banco
O admin do contêiner é dono das tabelas e só roda o init.sql. A API usa din_din_app, que só lê e grava linhas. Sem BYPASSRLS, essa role também deixa o caminho aberto para RLS no futuro.
Migração de dados explícita
O init.sql não adivinha de quem são as despesas antigas: elas ficam sem dono, invisíveis, até a migracao-001 passá-las para o e-mail informado, numa transação.
Erros num lugar só
O Express 5 encaminha a rejeição de funções async ao middleware de erro. Os controllers ficaram sem try/catch, e o handler central decide o que o cliente vê.
Falhar cedo na configuração
O config.js roda antes de qualquer conexão. Uma API que não sobe com o .env errado é mais segura do que uma que sobe e falha na primeira query.

F01API sem autenticação e dados sem dono: não existe mecanismo de isolamento

Autenticação por e-mail e senha. As rotas públicas POST /auth/registro e POST /auth/login devolvem um JWT assinado com HS256 que vale 1 hora. O middleware autenticar, montado em routes/index.js antes dos routers de despesas e categorias, exige Authorization: Bearer <token> e grava o dono em req.usuarioId; sem token válido, a resposta é 401. A tabela nova usuarios guarda o e-mail e o hash da senha, e despesas e categorias ganharam usuario_id NOT NULL com FK. No frontend, a tela de login cria a conta ou entra, e o token vai em toda chamada.

Por que assim: Um middleware só, na frente de todos os routers, protege também as rotas que ainda vão ser criadas: não depende de lembrar a autenticação rota a rota. O algoritmo é fixo na verificação (algorithms: ['HS256']), então um token com "alg": "none" é recusado. No login, e-mail inexistente e senha errada recebem a mesma resposta e levam o mesmo tempo: quando a conta não existe, a senha é conferida contra um hash falso, e o tempo de resposta não revela quem tem conta.

Como foi verificado: seguranca.test.js: as 10 rotas de dados sem token respondem 401 sem consultar o banco; token vencido, assinado com outro segredo, com alg: none, sem sub ou malformado também. auth.test.js: hash, registro, 409 e a mesma resposta 401 para e-mail inexistente e senha errada. Ponta a ponta com Postgres real (E4) e no navegador (E8).

Falta na sua máquina: Se o seu banco já tinha despesas, elas ficam sem dono e invisíveis até a migracao-001 passá-las para a sua conta (seção 8, passo 6).

F04A API conecta ao Postgres com o superusuário criado pela imagem

A API conecta com uma role própria, APP_DB_USER (padrão din_din_app), que o init.sql cria com NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE. Ela recebe só SELECT, INSERT, UPDATE, DELETE em despesas e categorias, SELECT, INSERT em usuarios e USAGE nas sequences. As tabelas continuam do admin do contêiner, que só aplica o init.sql. O config.js recusa subir se APP_DB_USER for igual a POSTGRES_USER.

Por que assim: Menor privilégio: se um dia houver uma injeção ou a senha da API vazar, o estrago fica em ler e alterar linhas, sem DROP, sem ler outros bancos e sem COPY … TO PROGRAM. A senha da role vem do ambiente do contêiner (\getenv), então não fica escrita em nenhum arquivo versionado. REVOKE CREATE ON SCHEMA public FROM PUBLIC impede a role de criar tabelas próprias.

Como foi verificado: Em Postgres 16 descartável: rolsuper, rolbypassrls, rolcreatedb e rolcreaterole falsos, e as tabelas pertencem ao admin (E3). Como a role da API, DROP TABLE, CREATE TABLE, ALTER TABLE, UPDATE usuarios, ler pg_authid e COPY … TO PROGRAM falham com 42501 (E5).

Falta na sua máquina: Pôr APP_DB_USER e APP_DB_PASSWORD no .env, recriar o contêiner e rodar o init.sql (seção 8, passos 2 a 4).

F05API e Postgres escutam em todas as interfaces de rede

A API escuta só em 127.0.0.1, e o compose publica o Postgres em 127.0.0.1:5434. O proxy do Vite passou a apontar para 127.0.0.1:3000 e ganhou a rota /auth.

Por que assim: Isso tira a dependência do Firewall do Windows: mesmo com um “Permitir” no aviso, ninguém de fora alcança as portas. O proxy usa 127.0.0.1 e não localhost porque localhost pode resolver para ::1 (IPv6), onde a API não escuta mais. Quando for preciso abrir para a rede, o caminho é um proxy com TLS na frente, não trocar o host.

Como foi verificado: netstat mostrou a API e o Postgres de teste só em 127.0.0.1. Num compose de teste, a porta saiu publicada em 127.0.0.1, e mudar o .env recriou o contêiner. O frontend funcionou pelo proxy do Vite (E8, E9).

F13Credenciais placeholder públicas aceitas sem validação no boot

Novo backend/src/config.js: um schema Zod valida o process.env assim que a API sobe. Ele recusa variável faltando, valor de exemplo (tudo que termina em _aqui), senha com menos de 12 caracteres, JWT_SECRET com menos de 32 e APP_DB_USER igual ao admin. A mensagem lista o nome de cada variável com problema, nunca o valor. db.js, token.js e server.js leem do config, não de process.env. O DATABASE_URL, duplicado e não usado, saiu do .env.example.

Por que assim: Falhar no boot é melhor que falhar na primeira query, ou subir com uma credencial publicada no repositório. Todos os placeholders do .env.example terminam em _aqui de propósito, para que uma regra só pegue todos. O .env.example traz o comando que gera um segredo aleatório.

Como foi verificado: config.test.js: 9 casos de recusa (o exemplo copiado sem editar, senha do admin ausente, curta ou de exemplo, senha da API ausente ou curta, JWT_SECRET ausente ou curto, API conectando como admin) e a mensagem sem o valor. Limitações das correções

Escolhas conscientes, com o limite de cada uma e quando revisar. Nenhuma reabre um achado da auditoria.

  1. Token no localStorage. Sobrevive ao recarregar a página, mas um XSS conseguiria lê-lo. Hoje não há XSS (categoria 5). A alternativa é um cookie HttpOnly com SameSite, que pede proteção contra CSRF.
  2. Sem refresh token nem logout no servidor. O token vale 1 hora e não pode ser revogado antes disso: "Sair" apaga o token só no navegador.
  3. O 409 do registro revela que um e-mail tem conta. O login não revela (mesma resposta e mesmo tempo), mas o cadastro sim. Fechar isso exige confirmação por e-mail.
  4. Rate limit na memória do processo. Zera quando a API reinicia e não é dividido entre instâncias. Com mais de uma instância, trocar por um store compartilhado, como Redis. Está marcado com shortcut: em limites.js.
  5. Paginação por OFFSET. Uma página alta fica lenta, e uma inserção no meio pode pular ou repetir um item entre duas páginas. Para listas grandes, trocar por cursor (WHERE id > $ultimo). Está marcado com shortcut: em api.js.
  6. JWT_SECRET também chega ao contêiner do banco. O compose lê o .env inteiro com env_file. Não sai da máquina, mas quem acessa o contêiner vê o segredo. Separar em dois arquivos resolve.
  7. Não há teste de integração versionado (M1). A suíte simula o banco. O isolamento entre dois usuários foi verificado com Postgres real por um script desta sessão, que não está no repositório.
  8. RLS não foi ligado. O isolamento depende do WHERE usuario_id em cada query. RLS com FORCE ROW LEVEL SECURITY seria a segunda tranca, e a role nova, sem BYPASSRLS, já permite ligá-lo.
  9. npm audit: 2 vulnerabilidades moderadas no nodemon, via minimatch. Afeta só o ambiente de desenvolvimento. A correção sugerida (npm audit fix --force) troca a versão do nodemon e não foi aplicada.
  10. Sair durante o "Desfazer". Se a pessoa clicar em Sair nos segundos do "Desfazer" de uma exclusão, a exclusão não é enviada, e a despesa continua lá no próximo login. É o lado seguro, mas difere de fechar a aba, que envia a exclusão.
  11. Dados de exemplo no npm run dev. Com a API desligada, o painel mostra os dados de exemplo, como antes, mas só para quem já tem um token salvo. Sem token, a tela é a de login.
