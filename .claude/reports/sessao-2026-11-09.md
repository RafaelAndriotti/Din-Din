## Item 1: parcelas no pagamento à vista

**Arquivo:** `backend/src/validators/despesasValidator.js`

**Problema.** `parcelas: z.number().default(1)` só preenche quando o campo vem `undefined`. `parcelas: -5` passava, e `2.5` estourava a coluna INTEGER do banco, virando 500.

**O que mudou.**
1. `e978391`: o `parcelas` saiu do schema `despesaAVista`. O `z.object` descarta chaves que não conhece, então qualquer valor enviado é ignorado.
2. `60e2a3a`: entrou o `.transform`, mas **encadeado no `z.enum` do `metodoPagamento`**. Bug: o `d` recebido era a string `"PIX"`, e o `{ ...d }` de uma string gera `{0:"P",1:"I",2:"X", parcelas:1}`. Isso iria para `metodo_pagamento` no banco.
3. `f51ea6a`: o `.transform` foi para depois do `.extend({...})` e passou a agir sobre o objeto inteiro:
   ```js
   export const despesaAVista = despesaBase.extend({
       metodoPagamento: z.enum(['PIX', 'DEBITO'])
   }).transform((d) => ({ ...d, parcelas: 1 }))
   ```

**Para que serve.** Despesa à vista sempre grava `parcelas: 1`, venha o que vier do cliente.

**Lições.**
- Cada método do Zod age sobre o schema em que foi chamado: no campo, mexe só no campo; no objeto, mexe no objeto todo.
- `.default()` preenche ausência e não substitui valor. Para forçar um valor, use `.transform()`.
- Depois do `.transform()`, o schema deixa de ser um `ZodObject` e perde `.extend()` e `.pick()`. Se precisar estender, faça antes do transform.

**Verificar no banco.** Despesas PIX/DÉBITO gravadas entre `60e2a3a` e `f51ea6a` podem ter lixo em `metodo_pagamento`.

## Item 2: validação do `:id` com middleware `validate`

**Problema.** `req.params.id` chegava como string direto no `$1` do Postgres. `/despesas/abc` ou `/despesas/99999999999` estouravam no banco e voltavam 500. Mas é erro do cliente, então deve ser 400, sem nem chegar ao banco.

### 2.1 Schema do id: `backend/src/validators/idSchema.js` (novo)
```js
id: z.string().regex(/^\d+$/).transform(Number)
     .pipe(z.number().int().positive().max(2147483647))
```
- `regex(/^\d+$/)`: só aceita dígitos. Rejeita `"abc"`, `"-1"`, `"1.5"`, `"1e3"` e `""`.
- `transform(Number)`: o texto vira número.
- `.pipe(...)`: valida o número resultante. `positive` barra 0, e `max` é o limite do INTEGER/serial do Postgres.
- Primeira versão (corrigida no `cb77a6e`): `.coerce` encadeado em `z.string()`. Não existe: o `coerce` só funciona como ponto de partida (`z.coerce.number()`). O erro acontecia já no import e derrubava 3 suítes de teste.

### 2.2 Middleware genérico: `backend/src/middleware/validate.js` (novo)
```js
export const validate = ({ params, body, query }) => (req, res, next) => {
    req.validacao ??= {};
    for (const [parte, schema] of Object.entries({ params, body, query })) {
        if (!schema) continue;
        const r = schema.safeParse(req[parte]);
        if (!r.success) return res.status(400).json({ message: "Dados invalidos", erros: r.error.issues })
        req.validacao[parte] = r.data;
    }
    next();
};
```
- **Para que serve:** substitui o `validarDespesa` e o `validarCategoria`, que eram cópias com só o schema trocado. As regras ficam nos schemas, e o `validate` só aplica.
- **Por que é uma "fábrica" (função que devolve função):** o Express exige que o middleware tenha a forma `(req, res, next)`. A 1ª chamada, `validate({ body: schema })`, acontece ao montar a rota e guarda o schema (closure). A 2ª chamada é o Express, a cada requisição.
- **Por que `req.validacao`:** no Express 5, `req.query` é só leitura. Guardar tudo num lugar próprio também deixa claro o que é dado validado e o que é dado cru.
- **`??=` e não `= {}`:** se duas chamadas do `validate` rodarem na mesma rota, a segunda não apaga o resultado da primeira.
- **Formato `{ message, erros }`:** é o que o frontend já lê (`api.js`, `body.erros`).
- **400 direto, por enquanto:** sem `errorHandler`, um `next(err)` cairia no handler padrão do Express e viraria 500 em HTML. Quando o item 4 existir, troca-se uma linha por `next(err)`.

### 2.3 Remoção das funções antigas (`d58c8da`)
O `validarDespesa` e o `validarCategoria` saíram dos validators. Os schemas continuam e são passados para o `validate`.

### 2.4 Rotas (`cb77a6e`): `despesasRoutes.js` e `categoriasRoutes.js`
```js
routes.get('/x/:id',    validate({ params: idParamsSchema }), ...)
routes.post('/x',       validate({ body: schema }), ...)
routes.put('/x/:id',    validate({ params: idParamsSchema, body: schema }), ...)
routes.delete('/x/:id', validate({ params: idParamsSchema }), ...)
```
Bugs encontrados no caminho e já corrigidos:
- **`validate` passado sem ser chamado** (`routes.post('/x', validate, ...)`): o Express executava a fábrica como middleware, o `next()` nunca era chamado e a requisição ficava pendurada. Nos testes, aparecia como `Test timed out in 5000ms`.
- **Categorias validadas com `despesaSchema`:** categoria válida voltava 400.
- **Faltava o import de `idParamsSchema`** em `categoriasRoutes.js`.

### 2.5 Controllers (`cb77a6e`)
`req.params` e `req.body` viraram `req.validacao.params` e `req.validacao.body` nos dois controllers.
- **Para que serve:** o `validate` não sobrescreve o `req.params` nem o `req.body`. Lendo o cru, o id ia como `"1"` (texto), e o `parcelas: 1` do transform e os defaults do Zod se perdiam. Validar e depois usar o dado cru torna a validação inútil.
- **Regra:** depois do `validate`, o controller só lê `req.validacao`.
