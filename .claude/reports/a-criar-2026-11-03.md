## CRI-1. Middleware central de erros e classes de erro

- **O quê:**
  - Uma classe base `AppError` (com status e código) e subclasses (`NotFoundError`, `ConflictError`...).
  - Um handler de 404 para rota inexistente.
  - **Um** middleware de erro com 4 argumentos, registrado por último no `app.js`. Ele traduz:
    - `AppError` para o status do próprio erro;
    - `ZodError` para 400;
    - o erro do body-parser (`entity.parse.failed`, `entity.too.large`) para 400 e 413;
    - os códigos do pg `23505` para 409, `23503` para 409/422, `23514`, `22P02` e `22003` para 400;
    - o resto para 500 genérico, logado no servidor.
- **Depende de:** COR-6 resolvido.
- **Estudar:** "Express 5 error handling" (rejeição de função async vai direto para o `next(err)`); "PostgreSQL Error Codes" (apêndice A da documentação); `instanceof` com classes que estendem `Error`.
- **Pronto quando:**
  - Nenhum controller tem `try/catch`.
  - `grep -rn "error.message" backend/src` não acha nada que vá para a resposta.
  - Os curls do COR-4 e do COR-5 devolvem JSON com o status certo.
  - Existe teste para 404, 409 e 500 genérico.

## CRI-2. Envelope de resposta padronizado

- **O quê:**
  - Um formato único de erro, produzido só pelo handler do CRI-1. Recomendado: `{ erro: { codigo, mensagem, detalhes } }`, ou a RFC 9457 (Problem Details).
  - Uma regra única de sucesso: recurso puro em GET/POST/PUT, 201 no POST (com cabeçalho `Location`, opcional) e 204 sem corpo no DELETE.
  - Ajustar o `frontend/src/services/api.js:63`, que hoje lê `body.erros`.
- **Depende de:** CRI-1, D2, D3.
- **Estudar:** RFC 9457; "HTTP semantics RFC 9110", seções de status codes.
- **Pronto quando:** um 400, um 404, um 409 e um 500 têm as mesmas chaves, e o frontend mostra o erro de validação por campo com o formato novo.

## CRI-3. Middleware genérico `validate({ body, params, query })`

- **O quê:**
  - Um middleware só, que recebe os schemas e valida as três partes.
  - Em caso de erro, entrega o `ZodError` ao CRI-1 em vez de responder ele mesmo.
  - Substitui `validarDespesa` e `validarCategoria`.
  - Schemas separados para criação e atualização (COR-9) e para `params` (COR-3).
- **Detalhe do Express 5:** `req.query` é um **getter**, e atribuir a ele não funciona. Guarde a query validada em outro lugar (ex.: `req.validated`) ou leia de lá. Pesquise "Express 5 req.query getter".
- **Depende de:** CRI-1, CRI-2, D4 a D6, COR-11.
- **Estudar:** Zod 4 `z.coerce`, `z.strictObject`, `.extend`, `.partial`; OWASP API3 (mass assignment).
- **Pronto quando:**
  - Toda rota declara o que valida.
  - Os payloads do COR-1, COR-2 e COR-3 devolvem 400 sem tocar no banco (o mock do pool não é chamado).
  - Existe teste unitário do `validate` isolado.

## CRI-4. Migrations versionadas

- **O quê:**
  - Uma ferramenta de migration: `node-pg-migrate` se ficar com pg puro, ou Prisma Migrate.
  - Uma primeira migration "baseline", igual ao `init.sql` de hoje.
  - Scripts `npm run migrate:up` e `migrate:down`.
  - O `init.sql` deixa de ser a fonte da verdade.
- **Por quê:** `CREATE TABLE IF NOT EXISTS` não altera uma tabela que já existe. Sem migrations, o seu banco, o de teste e o de outra máquina divergem sem ninguém perceber.
- **Depende de:** decisão pg ou Prisma.
- **Estudar:** "node-pg-migrate getting started" ou "Prisma Migrate baseline"; a tabela de controle de migrations; migration reversível.
- **Pronto quando:**
  - Num volume novo, `docker compose up` + `npm run migrate:up` criam o schema inteiro.
  - O `down` desfaz a última migration.
  - O `CLAUDE.md` passa a mandar rodar migrations em vez do `psql < init.sql`.

## CRI-5. Remodelagem do banco (data, FK, timestamps)

- **O quê**, em migrations pequenas, uma ideia por migration:
  1. `data DATE NOT NULL` em despesas. Num app financeiro, sem data não existe "gastos de outubro". As linhas antigas precisam de um valor antes do `NOT NULL`.
  2. `categoria_id` com FK para `categorias(id)` no lugar do texto livre `categoria`:
     - criar a coluna;
     - preencher a partir do nome (`UPDATE ... FROM categorias`);
     - tornar `NOT NULL`;
     - apagar a coluna antiga.
     - Crie um índice na FK: o Postgres **não** cria sozinho.
  3. `created_at` e `updated_at` como `TIMESTAMPTZ NOT NULL DEFAULT now()`.
  4. Os `NOT NULL` e `CHECK` do COR-7.
  5. Opcional: `GENERATED ALWAYS AS IDENTITY` no lugar de `SERIAL`.
- **Impacto na API e no front:** o contrato passa a usar `categoriaId`. A resposta pode trazer o nome via JOIN. O frontend precisa mudar.
- **Depende de:** CRI-4, decisão de `ON DELETE`, COR-11.
- **Estudar:** "PostgreSQL foreign keys ON DELETE"; "UPDATE ... FROM"; `timestamptz` vs `timestamp`; "identity columns".
- **Pronto quando:**
  - `INSERT` com `categoria_id` inexistente falha com `23503`, e a API devolve 409/422.
  - Apagar uma categoria em uso se comporta como foi decidido.
  - `\d despesas` mostra a FK, o índice e os CHECKs.

## CRI-7. Camadas service e repository

- **O quê:**
  - **repository:** só SQL, devolve dados ou `null`.
  - **service:** regras de negócio. Exemplos: "a categoria existe e está ativa?"; lançar `NotFoundError`; no futuro, "estourou o limite mensal?".
  - **controller:** só HTTP. Lê o `req` validado, chama o service, escolhe o status.
- **Por quê:** testar regra sem HTTP; trocar pg por Prisma mexendo numa camada só; tirar o SQL do controller.
- **Depende de:** CRI-1 (o service lança erro tipado) e CRI-6 (rede de segurança para refatorar).
- **Estudar:** "layered architecture", "repository pattern", injeção de dependência simples (passar o repository por parâmetro para testar o service).
- **Pronto quando:**
  - Nenhum controller importa o `pool`.
  - O service tem teste unitário com um repository falso.
  - A integração continua verde.

## CRI-8. Paginação, filtros, health check e versionamento

- **O quê:**
  - `GET /despesas?mes=2026-10&categoriaId=&status=&page=&limit=`, validado pelo CRI-3, com teto no `limit` e ordem determinística.
  - Resposta com metadados (`total`, `page`, `limit`), ou paginação por cursor.
  - Índices que atendem os filtros reais, ex.: `(data)` ou `(categoria_id, data)`.
  - `GET /health` com `SELECT 1`, no lugar do texto da raiz.
  - Prefixo `/api/v1`, ajustando o proxy do Vite.
- **Depende de:** CRI-3, CRI-5 (sem `data` não há filtro por mês), CRI-7.
- **Estudar:** "keyset pagination vs OFFSET"; `EXPLAIN ANALYZE`; "PostgreSQL multicolumn indexes"; filtro por intervalo de data (`data >= $1 AND data < $2`, que usa o índice, e não `date_trunc` na coluna).
- **Pronto quando:**
  - `limit=1000` é recusado ou limitado ao teto.
  - O filtro por mês usa o índice: o `EXPLAIN` mostra Index Scan com volume de dados.
  - `/health` devolve 200 com o banco no ar e 503 sem ele.

## CRI-9. Autenticação e dono dos dados

- **O quê:**
  - Tabela `usuarios` com email `UNIQUE` (em minúsculas) e hash de senha com argon2 ou bcrypt.
  - Cadastro e login.
  - JWT de vida curta (depois, refresh token com rotação).
  - Middleware que valida o token e põe `req.userId`.
  - `usuario_id NOT NULL` com FK em despesas e categorias.
  - `UNIQUE (usuario_id, nome)` em categorias, no lugar do `UNIQUE(nome)` global.
  - **Toda** query filtrando por `usuario_id`.
- **Por quê:** hoje qualquer pessoa lê, altera e apaga tudo. Isso é OWASP API1 (BOLA) e API2. Se o filtro por dono faltar numa rota, o usuário A lê a despesa do B só trocando o id.
- **Depende de:** CRI-4, CRI-5, CRI-7 (o filtro por dono fica no repository, num lugar só).
- **Estudar:**
  - OWASP API Security Top 10 2023, API1 e API2;
  - "argon2 vs bcrypt";
  - o segredo do JWT no `.env`, validado no boot (COR-13);
  - por que responder 404, e não 403, ao acessar o recurso de outro usuário.
- **Pronto quando:** existe teste de integração em que o usuário A tenta GET/PUT/DELETE na despesa do B e recebe 404, e a despesa do B continua intacta.

## Decisões pendentes

### pg puro ou Prisma

| | Prós | Contras |
|---|---|---|
| pg puro + node-pg-migrate | Você aprende SQL de verdade. Já está tudo escrito assim. Controle total de query, índice e `CHECK`. Uma dependência só. | Mapeamento snake/camel na mão. Sem tipos gerados. Mais código repetido (resolvido em parte pelo repository do CRI-7). |
| Prisma (ORM + Migrate) | Migrations e tipos gerados a partir de um schema. Menos boilerplate. Muito pedido no mercado. | Esconde o SQL, que é justamente o que você está aprendendo. Reescreve todos os controllers. `CHECK` e índices parciais exigem SQL na migration de qualquer jeito. A versão instalada é RC. |

Recomendação: pg puro agora, Prisma num projeto futuro para comparar. Em qualquer caso, remova o que não usar (COR-14).

### `ON DELETE` da FK de categoria

| | Prós | Contras |
|---|---|---|
| `RESTRICT` | Nunca perde informação. Força o usuário a decidir (mover as despesas ou desativar a categoria). Combina com o `ativo` que já existe. | A API precisa traduzir `23503` numa mensagem útil (409). |
| `SET NULL` | Apagar sempre funciona. | A coluna fica nullable. Aparecem despesas "sem categoria" e os relatórios por categoria perdem dados. |
| `CASCADE` | Simples. | Apaga despesas, ou seja, dinheiro registrado, como efeito colateral. Não use aqui. |

Recomendação: `RESTRICT`, com soft delete via `ativo = false`.

### Dinheiro na API: string decimal ou centavos inteiros

Hoje a API **recebe** `valor` como number e **devolve** como string (`"450.00"`, porque o `pg` não converte `NUMERIC`). O front converte com `Number()`. A entrada e a saída são assimétricas.

| | Prós | Contras |
|---|---|---|
| String decimal (`"450.00"`) | É o que o `pg` já devolve. Sem perda de precisão. Legível. | O cliente faz parse. Exige validar o formato (regex ou `z.string()` com refinamento). |
| Centavos inteiros (`45000`) | Inteiro é exato em JS até 2^53. Somar não acumula erro. Comum em APIs de pagamento. | Converte nos dois lados. É fácil esquecer e mostrar 100x o valor. Exige `BIGINT`/`INTEGER` ou conversão no SQL. |
| number com casas (`450.0`) | Simples. | Float: `0.1 + 0.2 !== 0.3`. Não use em soma de dinheiro. |

Recomendação: escolha uma e deixe a entrada **e** a saída iguais. Estude `pg-types` (`types.setTypeParser`) se quiser converter no driver.

### Fallback local do frontend

Hoje `getDespesas` mostra dados de exemplo só quando a rede falha e só em `import.meta.env.DEV`. O create, o update e o delete não simulam mais nada.

| | Prós | Contras |
|---|---|---|
| Manter (como está) | Dá para trabalhar no layout sem subir o backend. | Pode mascarar "esqueci de subir a API" durante um teste manual. Os dados de exemplo usam `parcelas: 0` e `categoria` em texto, e ficam desatualizados após o COR-11 e o CRI-5. |
| Desligar | Todo erro de backend aparece. Menos código para manter. | Para mexer no layout, precisa subir API e banco. |
| Desligar por variável (ex.: `VITE_USAR_FALLBACK`) | Explícito, e cada um escolhe. | Mais um ponto de configuração. |

Recomendação: deixar desligado por padrão enquanto faz CRI-1 a CRI-6, e atualizar os dados de exemplo junto com o CRI-5.

### Outras decisões abertas (do guia de 2026-10-29)

- **D2.** Formato do erro: envelope `{ erro: { codigo, mensagem, detalhes } }` ou RFC 9457.
- **D3.** Validação falha com 400 ou 422. Use um só. O front hoje trata 400.
- **D4.** Parcelas: ver COR-11.
- **D5.** `metodoPagamento`: enum com os rótulos atuais do front (`'PIX'`, `'Cartão de Crédito'`) ou com códigos estáveis (`'pix'`, `'cartao_credito'`). Os códigos são melhores, mas mexem no front.
- **D6.** Campo desconhecido no body: descartar (`z.object`) ou rejeitar (`z.strictObject`). Recomendado: rejeitar.
- **D7.** PATCH: depois do CRI-3.
